The problem, and what it unlocks

An AE starts the day in five systems deciding who to call, and most outbound goes out with no real reason to call. The rules are known; nobody applies them to a whole book before 9:00.

The skill applies them, every morning, the same way:

  • Ranks the book by rule: overdue deal work and next steps older than 14 days first; a deal is never buried under outbound.
  • Finds the why now with Apollo: a company posting a sales operations role is building the team that buys; that posting, dated, becomes the reason to call.
  • Drafts every touch and holds each email to the written standard before the rep sees it.

What it unlocks

  • The first hour goes to calls, not tabs.
  • Every outbound touch stands on a dated, checkable fact.
  • The CRM improves each morning: fresh readiness with its reasons and a task per next step, because the rep only says yes.

What I assumed

  • Each system's permissions are the right scope, so everything runs as the rep.
  • The ICP (buyer titles, size, signal windows) is RevOps owned, in a file, not code.
  • Calls and tickets live in Salesforce (a Gong object, Cases), as at most companies.
  • Reps forgive a gap they can see: a source that fails reads "Not checked".

Systems

Salesforce Developer Edition (read and write), Apollo REST API (bulk enrichment, job postings, news), Claude (the skill's agent, or the API with structured output for an unattended 8:00 run), Slack (Socket Mode, so /plan and buttons need no public server). Runs on a laptop, outbound only. The headless run can call three scripts and nothing else; it can never write to Salesforce.

The discussion questions

Why a skill, a script, or a direct MCP call?

Each does what it is best at. API calls fetch facts. Code decides order, safety and what may be shown, so every rule is a test. Claude writes. "Rank by these rules" in a prompt is a request; in code it is a guarantee. The skill file on top tells the agent when to run, in what order, and what it must never do. Apollo's MCP is wired in for people search on plans that include it.

How the data is shaped for the model

One block per account: a key, a category, a why now, a contact token, dated facts each labeled with its source. Unattended, the response schema's key is an enum of the plan's account ids, so a missing or invented account is impossible to return silently.

What I left out on purpose

Sending email or drafts. Any write without approval. A stored copy of CRM data. A model score for ranking. Mobile numbers. A hosted server.

Where AI helped, and where I did not trust it

Claude Code wrote most of the code and tests under review. Real runs caught what the suite did not:

  • Claude's own email had a five word subject against a limit of four: dropped by the checker.
  • The AI written checker was wrong too: it read "Thanks for reviewing..." as a sign off and dropped a good email. Fixed with a test that failed first.
  • Apollo tied off topic and bad news to accounts (a security flaw at GitLab, an investigation at Braze). Headlines must now name the company, and an email built on bad news is dropped.
  • Apollo's docs said its MCP gives people search on any plan; the account refused it. Tested every endpoint instead of trusting the docs.
  • Ten rules broken on purpose; the suite went red each time.
What production needs

Tokenization enforced at the model boundary, each Slack user mapped to their own Salesforce login so reads and writes run as that rep, the listener on an always on host with a run ledger, an eval set built from reps' verdicts, and the outcome measured: replies and meetings booked against a holdout.
